Why Rebuild the Forge & Spark Website

The Forge & Spark website currently runs on Elementor, a page builder that stores page layouts as encoded data inside the WordPress database. That works well for visual editing, but it creates a significant limitation: the structure of the website is essentially unreadable to anything outside Elementor. That puts a ceiling on what AI and other tools can understand, search, and improve across the site.

What stays the same

The foundation of the website does not change.

  • The site stays on WordPress
  • The existing admin and logins stay the same
  • Pages, posts, images, and other content remain in WordPress
  • The team will continue managing content through the WordPress admin
  • No one needs to edit code to update the site

The change is what sits underneath the content.

Instead of Elementor controlling the page layout, editable content will be managed through ACF fields. These appear as clearly labelled fields in the WordPress editor, so updating copy, images, and other content remains straightforward and familiar.

What changes

The page layouts will be rebuilt using lightweight, hand-built PHP templates rather than Elementor. This means the underlying structure becomes plain, readable text instead of encoded builder data.

That is important because it makes the entire website understandable to AI agents and other tools. Instead of having to work through individual pages visually, an AI agent can understand and work across the site as a whole.

For example, it could:

  • Audit every page for SEO opportunities
  • Check heading structures and accessibility issues
  • Identify missing or inconsistent alt text
  • Find messaging that has drifted from the brand framework
  • Identify inconsistencies across pages
  • Make systematic improvements across the site rather than working page by page

In other words, instead of asking someone to click through the site and make changes manually, we can increasingly ask the site to be reviewed, analyzed, and improved as a system.

Why this is worth doing

There are benefits beyond AI.

Performance: Leaner templates eliminate the additional code and processing associated with a page builder, which can improve page speed and Core Web Vitals.

Stability: Removing the page builder also removes a major software dependency and the class of compatibility and layout issues that can come with builder updates.

Maintainability: The site’s structure becomes simpler, more transparent, and easier to understand and maintain over time.

Future flexibility: Most importantly, the website is no longer dependent on a proprietary visual builder to understand its own structure. That gives us much more flexibility as AI-driven tools and workflows continue to evolve.

A proven approach

This is not an experimental rebuild. The same approach has already been implemented across five other websites, with two currently fully live.

For Forge & Spark, we are adapting and extending a proven pattern rather than starting from scratch.

This document will serve as the ongoing rebuild plan. It will be updated as decisions are made and components are developed, giving Forge & Spark an opportunity to review, provide feedback, and approve the work as we move through the rebuild.

Worth noting that regardless of where the architecture decision lands, a staging site is already set up and running, separate from the live site, so everything can be built and reviewed there before anything is promoted. The Novamira plugin that connects a WordPress site to AI tooling is installed and tested, and I use it heavily across five other sites. Recommended Architecture: Standalone Theme, No Page Builder

The suggestion on the table is to take Elementor out of the build entirely rather than run a hybrid setup, with pages shipping as PHP templates and ACF-driven content, on a standalone fs-theme rather than a child theme. WordPress stays exactly where it is: only the page builder comes out, and ACF keeps every piece of editable content in the admin where it is now. This is a recommendation for Forge & Spark to approve, not a settled decision.

The Migration, Step by Step
Same shape as the migrations already completed. Each step is done and checked before the next one starts.
✓

0  Read what exists

Audit the live site, plugins in use, and what Elementor is actually doing on each page. Partly done: the three Elementor gotchas from earlier migrations are already recorded.

1

1  Clone the theme into Drive

Clone Forge-Spark/fs-website into Website/fs-theme/. Nothing else can start until this exists locally. This is the next action.

2

2  Tokens

Confirm colors_and_type.css covers everything Elementor's Default Kit currently supplies. Elementor cannot be switched off until it does.

3

3  Scaffold

Stand up fs-theme as a standalone theme: style.css header with no Template: line, index.php, functions.php, theme.json carrying contentSize and wideSize, theme supports declared explicitly, and nav menus registered.

4

4  Build

First task is header.php and footer.php, then one test page with the menu working. Assess before going further. Then homepage, services, about, contact, and the Content With Purpose framework page.

5

5  Verify

Diff computed styles against a baseline captured before the switch. Screenshots are not sufficient, proven on an earlier migration. Walk every page type.

6

6  Switch

Update KINSTA_THEME_PATH to point at fs-theme before activating it. On an earlier migration the theme was activated first and the next deploy silently wrote to the dead directory.

7

7  Live

Manual push to live via MyKinsta, then verify on the live site in order. Rollback is git revert, not a theme switch.
